Speaking in parallel

How three models stream tokens at the same time without crashing into each other.

The line-cook kitchen

Imagine ordering pancakes, eggs, and bacon at a diner. One cook making all three in sequence is slow. Three cooks each grabbing one item at the same time is fast.

That is what Module 3 is about. The council does not interview its models one after another. It runs them in parallel and pipes their output to you live, one token at a time.

1

One cook, three orders

Pancakes finish. Then eggs start. Then bacon starts. Breakfast takes 30 minutes. This is what most simple Python code does.

3

Three cooks, one head chef

Every order starts at the same time. The head chef coordinates so nobody fights over the same pan. Breakfast in 10 minutes.

T

Plates by the bite

Instead of waiting for everything to finish, each cook slides food to you as soon as it is ready. You eat while you wait. That is streaming.

i
Why this matters when you direct an AI

When you tell an AI coding tool "make this faster" and it says "let us add async" or "stream the response," this module is what those words mean. If your AI implements streaming and the answer still appears all at once, the implementation is wrong.

What async actually means

Python normally does one thing at a time. asyncio is a library that lets it juggle many slow waits at once. The trick: a function marked async can pause itself while waiting on the network, freeing the runtime to start other work.

The actual code (council.py, lines 423-426)

CODE 
# Run all models in this batch concurrently
tasks = [asyncio.create_task(run_model(m)) for m in batch]
await asyncio.gather(*tasks)
PLAIN ENGLISH

A note for our future selves: we are about to fire off every model at the same time, not one by one.

For each model in this batch, we wrap its work in a task using asyncio.create_task. The instant a task is created, it starts running — Qwen, Gemma, and Mistral all kick off together.

Then we say await asyncio.gather(*tasks) — translation: wait here until every single task in the list has finished, then continue. gather is the head chef calling "all hands up when you are done."

async
The async keyword

Marks a function as pause-able. Without it, Python cannot juggle this work — it just blocks.

co
Coroutine

The thing an async function produces. A recipe. create_task hands the recipe to a cook so they actually start cooking.

L
Event loop

The traffic cop of asyncio. While one task waits on a slow model, the loop runs the other tasks. Nothing is ever truly idle.

Streaming, token by token

Parallel makes things fast. Streaming makes them feel fast. Instead of "wait 30 seconds, then get all the text," we get every chunk the model produces and forward it to the UI immediately.

There is a complication. ollama.chat() is synchronous — it blocks. We want async. So we use a classic bridge: a worker thread does the blocking work, and a queue ferries tokens out to the async loop.

The streaming bridge (council.py, lines 158-176)

CODE 
def run_stream():
    """Stream tokens from Ollama. Always signals 'done' via finally."""
    error_msg = None
    try:
        for chunk in ollama.chat(
            model=model,
            messages=[{"role": "user", "content": prompt}],
            stream=True
        ):
            token = chunk.get("message", {}).get("content", "")
            if token:  # Only enqueue non-empty tokens
                token_queue.put(("token", token))
    except Exception as e:
        error_msg = str(e)
        token_queue.put(("error", error_msg))
    finally:
        # Always signal completion so the consumer loop can exit
        token_queue.put(("done", None))
PLAIN ENGLISH

Define the worker function that will run inside a thread. Its only job is to pull tokens from Ollama and drop them on the queue.

Set up an empty error slot so we can remember any crash that happens.

Begin a try block — wrap the risky network work so a crash does not kill the whole app.

Call ollama.chat with stream=True. This returns a generator — we loop over it and each iteration is one new chunk of text from the model.

For each chunk, dig out the actual text. chunk.get("message", {}).get("content", "") means: be tolerant — if any field is missing, give me an empty string instead of crashing.

If the token has real text in it, push it onto the queue as ("token", token). The async side is reading this queue and forwarding each piece to the browser.

If anything explodes — network drop, model crash, bad response — catch the exception and put an ("error", message) on the queue so the UI can show what went wrong.

The magic line. finally guarantees that we always push ("done", None) onto the queue, even after an error. The async loop on the other side is waiting for that signal to stop reading. Without finally, one missed code path means the UI hangs forever.

i
Why a thread and asyncio?

asyncio is great when libraries are designed for it. ollama.chat() is not — it blocks. The thread is the airlock: the thread does the blocking work, the queue ferries tokens out, the async loop stays responsive. You can also imagine the thread as a daemon thread so it never outlives the app.

What can go wrong, and how the code defends

Two failure modes haunt every streaming system: the network gets too slow, or it gets stuck entirely. A third — the user just wants to cancel — also needs a clean answer.

10m

Total timeout

If a model has been streaming for more than 10 minutes total, something is very wrong. Cut it off and mark the response as timed out.

2m

Stall timeout

If 2 minutes pass with no new tokens, the model is probably stuck. Cancel and keep whatever output already arrived.

STOP

User-pressed Stop

When the user clicks Stop Deliberation, a shared signal flips. Every model checks it on every token and exits gracefully.

Snippet C — the two safety timeouts (council.py, lines 107-108, 188-197)

CODE 
STREAM_TOTAL_TIMEOUT_SECONDS = 600  # 10 minutes max for any single model response
STREAM_STALL_TIMEOUT_SECONDS = 120  # 2 minutes without receiving a token = stalled

# ... inside the consumer loop:
if elapsed > STREAM_TOTAL_TIMEOUT_SECONDS:
    logger.warning(f"[{get_display_name(model)}] Total timeout ({STREAM_TOTAL_TIMEOUT_SECONDS}s) exceeded")
    timed_out = True
    break

if time_since_last_token > STREAM_STALL_TIMEOUT_SECONDS:
    logger.warning(f"[{get_display_name(model)}] Stall timeout ({STREAM_STALL_TIMEOUT_SECONDS}s) - no tokens received")
    timed_out = True
    break
PLAIN ENGLISH

Two constants at the top of the file: ten minutes is the absolute ceiling, two minutes of silence is the stall threshold. Named constants like these are how senior engineers leave readable knobs for future-them.

Inside the loop that reads tokens off the queue, we check the total elapsed time. If we have been at this longer than 10 minutes, log a warning, flag the response as timed out, and break out of the loop.

Separately, we check the gap since the last token. If two whole minutes have passed without anything arriving, the model has stalled. Same drill: log, flag, break. Whatever text we have so far is kept.

Snippet D — the Stop button (council.py, lines 199-203)

CODE 
# Check if stop was requested
if stop_event is not None and stop_event.is_set():
    logger.info(f"[{get_display_name(model)}] Stop requested, halting stream")
    was_stopped = True
    break
PLAIN ENGLISH

A friendly reminder of what we are about to do: peek at the stop signal.

If a stop_event was passed in (it is an asyncio.Event) and somebody has flipped it on, we know the user clicked Stop.

Log it, flag the response as user-stopped, and break out of the loop. The same event is passed to every model, so all three notice the click at roughly the same instant.

!
Aha! moment

The finally: block from Snippet B is one of the most underrated tools in defensive code. Whenever you are bridging two systems — like a synchronous library to an async caller — always put the "signal done" in finally. Otherwise one path forgets, and your code hangs forever. The same logic applies to a deadlock or a race condition — most async bugs are really about who is waiting for whom.

!
The hidden trap

The real bug is what is missing right after this region: there is no finally: block that always puts ("done", None) on the queue. If ollama.chat() raises an exception type that is not caught, OR if the loop returns normally but forgets to signal "done," the consumer waiting on the queue would hang forever. The finally block guarantees the "done" signal always fires — no matter how the function exits. The line you clicked is where the missing safety net belongs.

The Chairman's Gavel

How Claude synthesizes the council, adds its own insights, and consults the web — with every contribution tagged for honesty.

The chief justice writes the opinion

Picture the chief justice of a supreme court. The other justices have argued, the clerks have written briefs, and now the chief sits down to draft the final opinion. They can agree with parts, override mistakes, add their own reasoning, and even send a clerk to fetch outside precedents.

In our codebase, that chief justice is Claude Opus 4.5. Claude is not one of the council models — it sits one level above them as the synthesizer.

1

Council Models

Local Ollama models answer the question independently. Each brings its own training, biases, and voice.

2

Peer Reviews

The same models grade each other anonymously on accuracy, insight, and completeness.

3

Consensus Score

Variance across the reviews collapses into one number: how much the council agreed.

4

Chairman

Claude reads all of the above and writes the final answer — synthesizing, correcting, and adding.

📜
The honesty signal

When you read the final answer, you might see little tags like [CHAIRMAN'S INSIGHT] or [WEB SOURCE] sprinkled through it. Those are not decorations — they are the chairman saying "this part did not come from the council, it came from me, or from a web search."

Why a different model on top?

The council is made of local 7B–70B models. The chairman is Claude Opus 4.5 — a frontier model running through the Anthropic API. Why the split?

🧠
Diversity from the council, quality from the chairman

Many small models give you a wide net of perspectives. One strong model on top gives you a careful editor who can spot mistakes none of them caught.

⚖️
If Claude were on the council, it would dominate

Putting a frontier model next to 7B models in the peer-review stage would just produce four agreeing voices. We would lose the diversity that makes the council worth running.

🔍
The chairman gets tool use — the council does not

Claude can call a web search mid-answer to verify a fact. The local Ollama models cannot. That capability gap is exactly the point of having a separate chairman.

💡
Aha! Tool use is the unlock

Tool use (also called function calling) is the single biggest unlock in modern LLM APIs. The model becomes a decision-maker that orchestrates external systems, not a text generator that only knows its training data. Any time you want an AI app to look something up, run a calculation, or call your database — this is the pattern.

The marching orders

Before Claude writes a word, we send it a long system prompt that tells it exactly how to behave. Two fragments matter most: permission to add independent insights, and permission to call web search.

Both fragments share one rule — if you add it, tag it. That tagging rule is what makes the final output honest.

Fragment 1 — Independent thinking

CODE 
# Independent thinking instructions
"""
CHAIRMAN'S INDEPENDENT ANALYSIS:
As Chairman, you are not limited to just summarizing the council's responses. You should:
- Add your own expert insights and analysis that go beyond what the council provided
- Identify gaps in the council's responses and fill them with your own knowledge
- Correct any factual errors you notice, even if the council members agreed on them
- Provide additional context or nuances the council may have missed

When you add independent insights, clearly mark them with [CHAIRMAN'S INSIGHT] so users know this came from your analysis rather than the council.
"""
PLAIN ENGLISH

Here is the chunk of prompt text we paste in for the independent-thinking rule.

We open a triple-quoted Python string and announce a new role: CHAIRMAN'S INDEPENDENT ANALYSIS.

We give Claude explicit permission to go beyond summarizing — to actually think for itself.

If the council missed something, Claude should fill the gap with its own knowledge.

If the council made a mistake — even one they all agreed on — Claude should correct it.

If there is useful nuance nobody mentioned, Claude should add it.

And here is the rule that makes it honest: anything Claude adds on its own must be tagged [CHAIRMAN'S INSIGHT] so the reader can tell.

Fragment 2 — Web search permission

CODE 
# Web search instructions
"""
WEB SEARCH CAPABILITY:
You have access to web search to verify facts or find current information. Use it when:
- Council responses conflict and you need to verify which is correct
- The question involves recent events or rapidly changing information
- You want to supplement the council's knowledge with additional sources

When you use web search, mark information from it with [WEB SOURCE] so users know its origin.
"""
PLAIN ENGLISH

This is the second prompt chunk — it tells Claude it has a search tool available.

We give Claude three trigger conditions for when to actually use the tool.

First trigger: the council disagrees and Claude needs a tiebreaker.

Second trigger: the question is about recent events that the council's training data is too old for.

Third trigger: Claude simply wants to back up the council with extra sources.

And the same honesty rule: any fact pulled from the web has to be tagged [WEB SOURCE].

🏷️
Why explicit attribution matters

When AI outputs blend multiple sources, it becomes impossible for the reader to know what is verified versus invented. Forcing the model to tag its own sources is one of the easiest, most underrated techniques for trustworthy AI — and it costs you almost nothing to add.

What a tool definition looks like

Telling Claude "you have web search" in prose is not enough. We also have to hand it a JSON schema that names the tool, describes it, and lists its inputs. The model reads the schema and decides when to call it.

CODE 
WEB_SEARCH_TOOL = {
    "name": "web_search",
    "description": "Search the web for current information to supplement council responses. Use this when you need to verify facts, get up-to-date information, or find information the council members may have missed.",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "The search query to look up"
            }
        },
        "required": ["query"]
    }
}
PLAIN ENGLISH

We are defining a single tool the model can call. The whole tool is a Python dictionary.

First field: the tool's name. The model literally writes this name when it decides to call it.

Then a long human-readable description. This is how the model decides when to reach for the tool — so it pays to be specific.

Now the input schema — a nested form that says "if you call this tool, here is the shape of arguments you must pass."

The arguments are an object with one field inside it.

That field is called query and it has to be a string.

And a description so the model knows what to put in there.

We close out the properties block.

Finally we mark query as required — the model is not allowed to call the tool without one.

Adapting to low consensus

Remember the consensus score from Module 5? It does not just sit there as a meter for the user — it actually changes what gets sent to Claude. When agreement is low, the chairman's prompt grows a new section.

CODE 
# When consensus is low, emphasize the importance of addressing disagreements
if consensus.level == "low":
    disagreement_emphasis = """
IMPORTANT: The council shows LOW CONSENSUS on this topic. This indicates the question may be complex, subjective, or have multiple valid perspectives. Pay special attention to:
- Why different council members reached different conclusions
- What underlying assumptions or values might explain the disagreement
- Whether the disagreement reveals important nuances the user should know about
- Present multiple perspectives fairly rather than forcing artificial agreement
"""
PLAIN ENGLISH

A comment reminds us why this branch exists: low agreement should change the chairman's behavior.

We check the consensus level. If it is "low," we build an extra instruction block.

We open a new triple-quoted string and announce LOW CONSENSUS at the top so Claude cannot miss it.

First focus: ask Claude to think about why the council split.

Second focus: surface the underlying assumptions or values driving the disagreement.

Third focus: tell the user if the disagreement itself is meaningful.

And the punchline: do not paper over the split — present multiple perspectives fairly instead of pretending the council agreed.

🔗
Cross-module wiring

The variance math from Module 5 produces a label — "low" / "medium" / "high" — and that label flips this if statement on or off. So Stage 2's review math literally rewrites Stage 3's prompt. That cross-stage data flow is what makes the pipeline feel like one organism instead of three scripts taped together.

Composition tracking + quiz

After Claude finishes writing, we do one last bookkeeping step: we measure what fraction of the final answer came from where. That breakdown becomes the three-segment meter you see in the UI.

CODE 
@dataclass
class ResponseComposition:
    """Tracks the source composition of the chairman's synthesis."""
    council_contribution: float  # 0-100, percentage from council model responses
    chairman_independent: float  # 0-100, percentage from chairman's own analysis
    web_search_used: float  # 0-100, percentage from web search
    web_searches_performed: list[str]  # List of search queries performed
    chairman_insights: list[str]  # Key insights added by chairman independently
PLAIN ENGLISH

The @dataclass decorator is shorthand for "make this a tidy data container without me writing boilerplate."

We define a dataclass called ResponseComposition.

A one-line docstring tells future readers what this object is for.

First field: what percentage of the answer came from the council models (0–100).

Second field: what percentage was Claude's own analysis. These are the bits tagged [CHAIRMAN'S INSIGHT].

Third field: what percentage came from web search. The three percentages always sum to 100.

Fourth field: the actual list of search queries Claude ran — useful for the audit trail.

Fifth field: the list of insights Claude added on its own — also for the audit trail.
